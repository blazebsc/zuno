# Xilem — benchmark report

- **Branch / commit**: `gui/xilem`
- **Framework + version**: xilem `0.4.0` + masonry `0.4.0` (crates.io), vello renderer
- **Renderer actually used**: **vello over wgpu with an NVIDIA GPU context** —
  `nvidia-smi` shows `./target/release/zuno-xilem` holding **473 MiB** of video
  memory during the scroll phase on the RTX 4070
- **Build**: `cargo build --release -p zuno-ui-xilem` — clean release build,
  **zero warnings**; binary 27,387,784 bytes (~26.1 MiB), fully native
  (`ldd` shows only `linux-vdso`, `libasound`, `libgcc_s`, `libm`, `libc` —
  Vulkan/GL arrive via runtime dlopen through wgpu)

## Implementation notes

- **List virtualization approach**: none — xilem 0.4 / masonry 0.4 has no
  production virtualized list, so **all 5,000 rows are resident**, exactly like
  iced. Masonry does ship an experimental `VirtualScroll` widget, but it has no
  scrollbar, no state-driven scroll API in the Xilem view layer, and documented
  MVP caveats, so it cannot serve the bench protocol. The number is the result.
- **Scroll driving**: a small custom view (`widgets::scrolled`) maps the bench
  fraction onto `Portal::set_viewport_pos` — a hard jump, no easing, the worst
  case. Xilem's stock `portal` view exposes no state→widget scroll path.
- **Bench parking matches iced**: the driver is constructed ~0.5 s after the
  first frame; the app parks at Library ▸ Songs on the first `ScrollTo`
  (startup/idle samples are the home view, same methodology as iced).
- **Custom widgets** (`native/ui-xilem/src/widgets.rs`, required because xilem
  0.4's set is still maturing): `KeySink` root (global shortcuts + resize
  reporting via the window's focus fallback), hover-aware `HotButton`
  (hover backgrounds, card play-scrim + red pill and the animated 3-bar
  indicator painted in `post_paint`), `DragStrip` + `WindowControl`
  (frameless chrome), vector `Glyph` icon set, `Scrolled`.
- **No composition gaps**: xilem 0.4 already ships `slider`, `image`,
  `text_input`, `checkbox`, `portal` — seek/volume sliders, artwork images and
  the search field are all native widgets.
- **Artwork**: shared `core::ArtworkCache` (96-cover LRU) → masonry
  `ImageBrush` handles; a `(seed, size, round)` map avoids re-upload; artist
  art gets a CPU circle alpha-mask (masonry has no clip-to-circle image).
- **What was animated**: playing-bars indicator (frame counter on the 16 ms
  tick), card hover scrim + play pill, seek/volume sliders live-drag,
  per-frame playhead.
- **Keyboard interactions shipped**: Space, ←/→ seek ±10 s, Esc back/clear,
  M mute, Q queue toggle, S shuffle, R repeat, Ctrl-K navigates to Search.
  NOT shipped: ↑/↓ selection, Enter to play, PgUp/PgDn scroll, `/` shortcut,
  drag-reorder in the queue (spec marks reorder "should").
- **Design tokens**: Zuno palette (`#0a0a0a` / `#2a2a2a` / `#ff0033`), bundled
  Inter variable font, 52 px rows, 176 px cards, 232 px headers, 44 px custom
  titlebar, 220 px sidebar, frameless 14 px rounded shell with native-feel
  min/max/close.

### Visual divergences from the spec (honesty over polish)

- Scrollbars are masonry's chunky default style (bright on dark) on every
  shelf and page — always-affordance, no overlay/fade styling API in 0.4.
- Sidebar never collapses below 1000 px width (fixed 220 px); the album grid
  reflows with window width. Queue panel squeezes rather than overlays.
- Ctrl-K navigates to the Search view but does not move keyboard focus into
  the text field (no programmatic focus API reached from the view layer).
- No ↑/↓/Enter/PgUp/PgDn list keyboard control; selection is bench/keyboard
  only, no mouse multi-select.

### What xilem made hard/easy (for the next evaluator)

- Easy: the Elm-style `fn view(&mut State) -> impl WidgetView` kept app logic
  trivial; `slider`/`image`/`text_input` all exist; zero-warning build.
- Hard: no virtualized list; no state-driven scroll/​focus APIs (custom
  masonry widgets + views required); flex sizing silently overflows instead of
  constraining — the first build pushed the player bar out of the window
  (only the per-window screenshot caught it; fixed with an explicit flex on
  the content row, verified visually). Read the local
  `~/.cargo/registry/src/*/masonry-*/src/` source before writing code; the
  0.4 API surface moves fast and docs lag it.

## Honest issues observed

- Memory is the headline: ~450 MB home (iced: ~204 MB) and ~1052 MB with the
  5,000-row list (iced: ~489 MB), peak ~1120 MB. Per-row/widget overhead in
  masonry 0.4 is roughly 2× iced's — the cost of an early-stage toolkit with
  no row recycling.
- Scroll-phase CPU is 84–85% of one core for the full 20 s; no dropped-frame
  counter exists in-app, but the triangle-wave scroll stayed responsive.
- First scroll into the 5k list hitches briefly (~0.5 s) while all rows and
  artwork handles build; smooth afterwards.
- 40 threads is wgpu + cpal + async runtime overhead, not a problem.
- A first `--bench` attempt parked at Library ▸ Songs at driver construction
  (startup sample 811 MB, list built before the sample); redone to park on
  first `ScrollTo` like iced so the phases are comparable. Only the two runs
  above (final binary, final methodology) are reported.
