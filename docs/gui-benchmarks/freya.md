# Freya — benchmark report

- **Branch / commit**: `gui/freya`
- **Framework + version**: freya `0.5.0-rc.9` (crates.io) + freya-engine `0.5.0-rc.9`
  (Dioxus + Skia)
- **Renderer actually used**: **Skia over GL on NVIDIA** — the process holds a
  GPU context in `nvidia-smi` (39–57 MiB video memory across runs); the binary
  links EGL/GL/GLX directly (`libEGL.so.1`, `libGL.so.1`, `libGLX.so.0`).
- **Build**: `cargo build -p zuno-ui-freya --release` — clean, zero warnings.
  Binary 39,082,936 bytes (~37.3 MiB). (Incremental release link ~6 s; the full
  dependency tree was already compiled by the earlier scaffolding attempt, so
  no clean-build time was measured.)

**Reading the variance honestly**: startup/idle are identical across runs
(~163 MB). The scroll-phase delta (206 / 169 / 166 MB) tracks how many list
rows actually got laid out, which tracks delivered frame rate: with a visible
window (run 1) the full sweep materializes all ~5,000 row covers (~32 MB of
40 px RGBA plus Skia wrappers); under the screen lock (runs 2–3) the
compositor stops presenting, freya's frame ticker throttles to near-zero
(run-3 CPU was 0.9 s over 48 s), and most rows are never built — yet the
time-based schedule still completes and exits 0. Run 1 is the representative
interactive measurement. A sibling agent's `zuno-gpui --bench` was running
concurrently with all three runs (shared box, load ~3.5–5), so CPU seconds
carry that noise too.

## Implementation notes

- **List virtualization approach**: freya's lazy `VirtualScrollView` for the
  Library ▸ Songs 5,000-row list (`new_with_data_controlled` + a
  `ScrollController` from the `use_scroll_controller` hook, `item_size(52)`).
  Only visible rows are built per frame — hence idle→scroll is +~43 MB of
  progressively materialized row covers, not +300 MB of resident rows.
  Every other list (album/playlist/search-top-tracks, sidebar playlists,
  shelves, grids) is fully realized, like iced.
- **Scroll driving**: `scroll_to_y(-(f * 259_000.0) as i32)` per bench tick —
  a hard jump, no easing; freya scroll offsets are negative-downward and the
  controller clamps against laid-out bounds.
- **Artwork**: shared `core::ArtworkCache` (96-cover LRU, `&self` getter so
  render can call it through a read guard) → `ImageHandle::from_rgba` with
  `AlphaType::Opaque` → process-wide `(seed, size) → handle` map in a
  `OnceLock<Mutex<…>>` so re-renders don't re-upload. Seeds match iced
  (`album_seed` for rows/cards, `artist_seed`/`playlist_seed` elsewhere).
- **State/frame loop**: the whole `AppState` lives in one global
  `State<AppState>`; a single `spawn_forever` task paced by
  `RenderingTicker::tick()` (i.e. once per freya frame) runs `state.tick()`,
  the search-field sync, and the bench schedule, then sends
  `UserEvent::RequestRedraw`. Any write re-renders the tree — simple, but
  reactivity is all-or-nothing (full tree rebuild per frame; the VSV keeps
  row work bounded).
- **What was animated vs static**: playing-bars indicator (3 bars driven by
  the frame counter), seek/volume sliders live-drag, per-frame progress
  times. Hover tints are instant swaps (no 120 ms fades — freya has an
  animation crate but wiring fades per row was skipped). No page transitions.
- **Keyboard interactions shipped**: Space play/pause, ←/→ seek ±10 s, ↑/↓
  move selection, Enter play selected, Esc back, M mute, Q queue toggle,
  S shuffle, R repeat, Ctrl-K and `/` go to Search. PgUp/PgDn currently just
  clear the selection (simplification, see below). Space/arrows/letters are
  disabled while the Search view is up so typing never toggles playback.
- **Visual divergences from the spec (honesty over polish)**:
  - Card hover shows the red play pill in a reserved footer row rather than a
    50 %-scrim overlay (no overlay/stacking API was used).
  - `TitlebarButton` (Minimize/Maximize/Close) is in the custom 44 px
    titlebar, but its default-theme icons are near-invisible on the dark
    background — present, subtle, physical click-testing blocked by the
    screen lock (see issues).
  - No window icon: freya 0.5-rc.9's `WindowConfig` exposes no icon setter.
  - Sidebar is fixed 220 px (no <1000 px collapse); New-albums grid is fixed
    4-per-row (not truly responsive); queue panel squeezes instead of
    overlaying at narrow widths.
  - Search results render core's capped buckets verbatim (≤300 tracks) —
    no additional UI cap.
  - Ctrl-K navigates to Search but does not move keyboard focus into the
    field (no programmatic-focus API found on `Input`).
  - The report screenshot's tile clips the window bottom (niri tile smaller
    than the 1280×800 request; red sliver at the cut is the play button top)
    — compositor artifact, not a layout bug (the player bar renders; it is
    visible in full-window captures).
- **What the framework made hard/easy**:
  - Easy: `VirtualScrollView` + `ScrollController::scroll_to_y` made the
    bench protocol almost trivial; `ImageHandle::from_rgba` matches core's
    RGBA cache 1:1; `TitlebarButton` actions are pre-wired; global
    `State<T>` + `write_unchecked` fits `AppState`'s interior-mutability-free
    API well.
  - Hard: `ScrollController::new` (and any `State` creation) panics outside
    Freya context, so it must be built inside render via
    `use_scroll_controller` and threaded down as a param — the probe caught
    this only at runtime. `child(x.into())` never infers (pass concrete
    element types; use `let …: Element` annotations where conversion is
    needed). `TrackView` carries no `album_id` — join via
    `library.track(id).album_id`. `Key::Named(NamedKey::Space)` does not exist
    in keyboard-types 0.8 (space arrives as `Key::Character(" ")`).
    `Slider`/`Input` ship light-theme defaults that need explicit theming
    for a dark app (sliders kept default here).

## Honest issues observed

- The screen locked mid-session (no password available to unlock): runs 2–3
  measured a non-presented window. Kept verbatim and labeled rather than
  discarded.
- Scroll-phase RSS varies with delivered frame rate (206 vs ~167 MB) — the
  number measures materialized rows, so any throttling (lock, contention)
  moves it. Compare idle/startup across branches, scroll with this caveat.
- One early build panicked in `main` (`ScrollController::new` outside
  context); fixed by hook creation, zero panics in 3×48 s bench runs plus
  smoke tests since.
- `ps` RSS mid-scroll (~169 MB at 22 s, run 3) trails the driver's report
  slightly — different sampling instants, both real.
- Not physically click-tested (lockdown): hover/press wiring follows the
  probe-verified `on_press`/`on_pointer_enter` API and compiles clean, but
  treat interaction polish as code-reviewed, not finger-tested.
- `freya` is an RC: `cargo build` is clean with zero warnings, but expect API
  churn before 0.5 stable (`use_scroll_controller`'s closure config,
  `GenerationalRef` read/write split, theme-preference plumbing).
