# Vizia — benchmark report

- **Branch / commit**: `gui/vizia` (report shipped with the branch's first
  commit, `feat: native vizia UI benchmark (gui/vizia)`; parent is
  `ebbb2be feat: shared native-GUI benchmark core (gui/base)`)
- **Framework + version**: vizia `0.4.0` (crates.io) — retained
  entity-component GUI, Skia renderer (`skia-safe 0.93.1` statically linked,
  OpenGL via glutin/EGL on Wayland), signals-driven bindings
- **Renderer actually used**: **Skia + OpenGL on the NVIDIA RTX 4070 Laptop
  GPU** — `nvidia-smi` shows `./target/release/zuno-vizia` as a graphics
  process with 117 MiB of video memory during the scroll phase
- **Build**: `cargo build -p zuno-ui-vizia --release` — incremental release
  rebuild ≈ 9 s; binary 37,298,968 bytes (35.6 MiB, Skia static). No build
  warnings. Dependency note: first clean build pays the usual skia-bindings
  cost (cached afterwards).

**The headline: the 5,000-row scroll phase is RSS-flat.** Entering Library ▸
Songs and sweeping the full list top↔bottom five times *lowers* resident
memory by ~2 MB versus idle and never wobbles more than 0.1 MB across 20
samples in either run. Vizia's recycled `VirtualList` keeps only ~15 live
row entities for the whole list, and the shared core artwork LRU bounds the
decoded covers, so scrolling 5,000 rows costs nothing measurable in RAM.
Compare iced (no virtualization): +285 MB at the same phase, 490 MB peak.
Total peak here: **149.6 MB**, roughly a third of iced's number, with the
playback phase running real rodio→cpal→ALSA audio and a live GPU context.

## Implementation notes

- **List virtualization approach**: vizia's `VirtualList` (recycled rows,
  ~15 live `ListItem`s for 5,000 rows). The bench's `ScrollTo(f)` maps 1:1
  onto the list's normalized 0..1 `scroll_y` signal — set every tick, a
  hard jump, no easing, exactly the protocol's worst case. Search results
  reuse the same view; album/playlist pages render their (small) full lists.
- **What was animated**: playing-bars indicator (custom `View` with a
  per-frame `needs_redraw` bound to a frame counter signal, only advanced
  while playing), hover colour fades + the card scrim/pill fade via CSS
  `transition` (120–150 ms), seek/volume sliders live-drag, per-frame
  playhead from `state.player.position_sec()`.
- **Keyboard interactions shipped**: Space play/pause, ←/→ seek ∓10 s,
  Esc back/clear-search, M mute, Q queue toggle, S shuffle, R repeat
  cycling, Ctrl-K focuses the search field (with a typing guard so letter
  shortcuts don't fire while typing). Vizia buttons are not
  keyboard-activatable, and ↑/↓/Enter/PgUp/PgDn row navigation did not ship.
- **Artwork bridge**: core's shared RGBA cache → PNG encode (`png` crate,
  fast compression) → `cx.load_image` (skia decode), keyed `art-(seed)-(size)`.
  PNG bytes are intentionally leaked for the process lifetime (bounded:
  ~600 covers at 40 px for a full songs sweep, plus per-view cover sets);
  skia's decoded copies are retained with `ImageRetentionPolicy::Forever`.
  The decoded-bitmap budget itself stays in core's 96-cover LRU.
- **Bench loop**: a 16 ms `EventContext` timer emits `Tick`; the model
  advances `state.tick()`, drives `BenchDriver`, and mirrors state into
  ~15 signals (`set_if_changed` everywhere) that the views bind. Note:
  vizia's `add_timer` registers a *stopped* timer — it must be started via
  `start_timer` on an `EventContext`.

### Visual divergences from the spec (honesty here is the point)

- Card titles clamp to **1 line**, not the spec's 2 (see layout notes below
  for why; long titles ellipsize instead of wrapping).
- Track-row text columns measure zero-width inside buttons (vizia quirk), so
  single-line ellipsis isn't enforced by the layout — long titles can
  visually crowd the duration column.
- No drag-reorder in the queue panel ("should" item, not shipped).
- Native window decorations; no 220→62 px sidebar collapse at narrow widths;
  the queue panel overlays via absolute positioning (works, but is not a
  real overlay layer).
- Tabular numerals: no `font-feature-settings` support in vizia's CSS, so
  durations rely on right-alignment (same mitigation iced used).
- No letter-spacing property exists in vizia's CSS dialect, so h1/h2
  tracking (-0.03em/-0.02em) is not applied.
- The screenshot was taken with the window fake-fullscreened on the test
  monitor (niri is a scrolling tiler and otherwise resizes the window per
  tile; the app itself requests 1280×800 with a 900×600 minimum).

### What vizia made hard/easy (for the next evaluator)

- **Easy**: the reactive model — `Signal` + `Binding` + `set_if_changed`
  made the whole app state-diffable for free; `VirtualList` was built for
  exactly this benchmark; one CSS stylesheet themes everything with real
  selectors and pseudo-classes; the bench protocol's 0..1 scroll fraction
  required zero math.
- **Hard — silent CSS pitfalls** (all found by dumping parsed rules offline
  with `vizia_style` itself, since the app swallows stylesheet errors):
  - A multi-value `padding: 1px 2px 3px 4px` shorthand doesn't just drop
    that declaration — it poisons neighbouring declarations, and in one
    case erased an entire rule (`.sidebar` lost all properties, hence no
    220px width and no player-bar height, rendering as an overlapped mess
    until found). Use `padding-left/right/top/bottom` only.
  - The default theme's `image { size: auto }` beats class-set
    width/height in some containers; size images with entity-level
    `.width(Pixels(..)).height(Pixels(..))` modifiers, which always win.
  - `ZStack` does not actually overlay its children reliably in 0.4 (its
    auto height measured 0 for 176px children); the card scrim is an
    absolutely-positioned sibling instead.
  - Auto-sized containers holding fixed-size children under-measure (a
    card column measured 27px for 224px of content); every height-critical
    container got explicit pixel heights, verified with a runtime entity
    bounds dump.
  - Adding an `Alignment::TopLeft` modifier (plus the matching CSS rule)
    reproducibly made the app exit cleanly at startup with no window and
    no error; reverted rather than root-caused — cards remain
    content-centered with the art flush at a fixed content height.
- Timers must be explicitly started (`add_timer` alone never fires) — the
  first bench attempt hung 48 s in silence until this was found.

## Honest issues observed

- The scroll phase is RSS-flat, but the **whole 48 s run costs 19–20% of one
  core**: the 60 Hz tick timer plus relayout/recycling on every scroll
  jump. Smooth, no visible stutter, but the timer never sleeps while the
  app is open (2.5% CPU even idle on the home view).
- Interactive (non-bench) sessions occasionally exited early (~3 observed
  deaths in the 30–60 s range, clean exit code, no panic, nothing in
  stderr) while I was aggressively toggling focus/fullscreen/workspaces in
  the compositor to stage screenshots. Never reproduced under `strace`, in
  plain 120 s runs, or in any bench run. Unconfirmed suspicion: interaction
  with the desktop session (the window repeatedly appearing on the user's
  focused workspace), not an app crash — but I cannot prove it.
- niri tiles the window to varying sizes between launches (~1280×800 to
  ~1800×1100 logical during these runs); the bench protocol does not pin
  window size (same as iced's run), which is one likely source of the small
  run-to-run RSS spread (147.9 vs 149.6 MB peak).
- Startup RSS (~150 MB) includes the Skia/OpenGL context, the full
  synthetic library, the Inter variable font, and the home view's artwork —
  before any list view is opened.
- 9 threads at exit: main + winit/glutin render + cpal audio + vizia
  internals. Single process throughout.
