# Slint — benchmark report

- **Branch / commit**: `gui/slint`
- **Framework + version**: Slint `1.18.1` (crates.io; `slint` + `slint-build`), winit backend
- **Renderer actually used**: **femtovg (OpenGL)** — the binary the numbers below come
  from contains no Skia symbols (verified: 0 `SkCanvas`/`skia_safe` symbols in
  `target/release/zuno-slint`). A build with the `renderer-skia` feature also
  compiles cleanly (+1m 29s incremental, 43.2 MB binary vs 31.2 MB); with both
  renderers compiled in the backend selector prefers Skia
  (`i-slint-backend-winit` `create_renderer`: the `enable_skia_renderer` cfg
  branch wins) — so the shipped `Cargo.toml` enables femtovg only, which is what
  was measured.
- **Build**: `cargo build -p zuno-ui-slint --release` — first full build
  2m 04s, binary **31.2 MB**, **0 compiler warnings**.

**The scroll phase is where virtualization pays.** The full 5,000-row model
(TrackRow structs with precomputed strings + 40 px artwork handles) is resident
from startup; sweeping the list top↔bottom every 4 s for 20 s — with a hard
`content-y` jump every frame — added **+3.9 MB (run 1) / +4.4 MB (run 2)**:
just the visible delegate pool (~13 rows). Both runs are perfectly flat
(min == max across all 20 scroll samples). Against the iced reference on the
same machine: peak **153–158 MB vs 488–491 MB** (~3.1× less), scroll-phase
delta **+4 MB vs +285 MB**, CPU **3.2–5.9 s vs 27.3–41.1 s** (7–12% vs
57–86% of one core), threads **9 vs 42**.

## Implementation notes

- **List virtualization approach**: Slint's `ListView` *is* virtualized — only
  visible delegates are instantiated (~13 rows of 5,000 on this window). The
  whole model is resident from startup inside the idle RSS; the bench scroll
  is driven by assigning `ListView.content-y` (a `ScrollView`-inherited
  two-way property) from a root `public function bench-scroll(frac)` that Rust
  calls via the generated `invoke_bench_scroll` — a hard jump, no easing, the
  same worst case the iced branch performs. This is the one framework in the
  bake-off where the 5k list does **not** cost hundreds of MB.
- **Grids**: Library ▸ Albums (600 cards) is a `ListView` over row-chunk
  structs (`ModelRc<GridRow>` where `GridRow.cards` is a nested model) — also
  virtualized. Card artwork is filled **lazily**: grid cards are created
  art-empty with a `needs-art` flag and a delegate `init` callback asks Rust
  for the (seed,size) cover, so a 600-card grid holds only ~visible decoded
  176 px covers. Home shelves (54 cards) and search shelves are pre-filled.
  Re-flow on window resize re-chunks the row models from Rust (window size
  polled each tick).
- **Queue panel** is a `ListView` too (sections NOW PLAYING / NEXT IN QUEUE /
  NEXT UP carried as a `header` field on the first row of each region), so a
  2,500-row queue also stays virtualized.
- **Models**: built as `VecModel`s and handed to the window once as
  `ModelRc`s; later updates mutate the `VecModel` in place (`set_row_data`),
  which updates delegates without resetting any scroll position.
- **What was animated vs static**: now-playing 3-bar indicator is pure markup
  (`animate height { iteration-count: -1; direction: alternate }`, three bars
  at 430/520/610 ms); hover backgrounds 120 ms; card hover scrim + red play
  pill fade-in 150 ms; shuffle/repeat/like/play-pause state colors. Static:
  everything else.
- **Keyboard interactions shipped**: Space (play/pause), ←/→ (seek ∓10 s),
  Esc (clear search / back), M (mute), Q (queue), S (shuffle), R (repeat),
  Ctrl-K and `/` (focus search, deferred one event-loop turn so the page is
  visible when focus lands). Not shipped: ↑/↓ row selection, Enter, PgUp/PgDn.
- **Design tokens**: exact `core::theme` palette (#0a0a0a / #2a2a2a /
  #ff0033 / #171717 / #a1a1a1), Inter variable font bundled via
  `import "../assets/Inter-Variable.ttf";` and set as
  `default-font-family`, 52 px rows, 176 px cards, 232 px heroes, 220 px
  sidebar (collapses to a 62 px icon rail < 1000 px width), 300 px queue
  panel overlay, 76 px player bar, pill buttons, rounded artwork.

### Visual divergences from the spec (honesty over polish)

- Card titles are single-line elided — Slint has no multi-line clamp
  (spec asks for a 2-line clamp).
- No `tabular-nums` font-feature control in Slint markup; duration/count
  columns are right-aligned instead (same mitigation the iced report notes).
- Native Wayland: the compositor (niri) draws no window decorations, so the
  app renders frameless with its own content edges — no 14 px-radius custom
  shell (spec "should").
- Scrollbars are the Fluent widget style; they are not restyled to Zuno's
  4 px hairline (Slint's std-widgets don't expose scrollbar styling).
- Queue drag-reorder not implemented (spec marks it "should").
- Songs-tab scroll position survives navigating away and back (the Library
  page is retained and only visibility-toggles), unlike a from-scratch
  rebuild — a small behavioral difference in Slint's favor.
- First bench scroll tick after the view switch may apply a stale viewport
  height for one frame (content-y is assigned before the new page's first
  layout); it self-corrects 16 ms later and does not affect the samples.

### What Slint made hard/easy (for the next evaluator)

- **Easy**: the virtualized list *and* its scroll position are directly
  drivable — `ListView` inherits `ScrollView`'s `content-y`, so the bench
  protocol is one property assignment. Declarative animations, `init`
  callbacks for lazy resources, and cheap-clone `slint::Image` handles make
  the (seed,size) cache trivial. Reading the local crate source
  (`~/.cargo/registry/src/*/slint-*`) before writing code paid for itself:
  `content-y`, `changed` handlers, `init`, `animate` semantics and the
  skia-vs-femtovg selector order were all confirmed there first.
- **Hard**: everything inside an `if cond:` element is fully encapsulated —
  no property or function access from outside — so the two pages Rust must
  reach into (Library for the bench scroll, Search for Ctrl-K focus) are kept
  always-instantiated with `visible:` switching instead. Generated component
  handles don't implement `Clone` (use `clone_strong()`), and Rust-side models
  must be **explicitly handed** to the window as `ModelRc` — forgetting this
  renders empty pages with no error or warning (the one real bug found while
  bringing the app up). Cross-component borrow discipline in the driver
  (models + `AppState` + artwork cache in one struct) needs field-level
  borrows, not method calls, in the same expression.

## Honest issues observed

- **The compositor gates measurement.** niri skips rendering windows that are
  occluded or lose their workspace — a retained-mode app then genuinely does
  almost no work. Two early runs with partially-occluded windows measured
  1–2% CPU (discarded as unrepresentative), and three further runs were
  closed mid-schedule by the active user session on this machine (report
  never printed — the app exits via `process::exit`, and an empty report is
  the tell-tale). The two reported runs had their window visible for the full
  schedule (verified with mid-run screenshots; the scroll-phase captures show
  different rows at different times, and 36.9% of the window's pixels changed
  between captures 6 s apart).
- Startup RSS differs between the two runs (121.7 vs 153.3 MB): the driver's
  t=0.5 s sample can land before or after the compositor maps the window and
  the first frame's GPU allocations land. The steady-state number is ~153 MB.
- The +4 MB scroll delta is the delegate pool (~13 visible rows), not the
  list itself — the 5,000-row model plus ~570 distinct 40 px covers are
  already inside the idle number.
- Scrolling the 5k list with hard jumps at 60 Hz costs 7–12% of one core and
  stays perfectly smooth in release; nothing visibly stuttered, and no frame
  drops were observed. CPU is lower than iced's mostly because iced
  re-layouts all 5,000 rows every frame while Slint instantiates only the
  visible ~13.
- Nine threads total (main + winit + GL + cpal/rodio audio); peak RSS
  153–158 MB including the GL context, the full library model, and the
  startup artwork set.
