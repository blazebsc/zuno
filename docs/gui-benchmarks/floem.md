## Implementation notes

- list virtualization approach: floem's **`virtual_list`** (Vertical,
  fixed 52 px items) over an `im::Vector<(usize, TrackId)>` rebuilt from
  `state.list_ids()` only when content signals change. Only visible rows
  exist as views; found in `~/.cargo/registry/src/*/floem-0.2*/src/views/`
  (`virtual_list.rs` / `virtual_stack.rs`). Bench scrolling drives
  `Scroll.scroll_to` with a `RwSignal<Option<Point>>` target
  (`f * (5000*52 − 560)`); actual offset/viewport tracked back via
  `Scroll.on_scroll` for PgUp/PgDn and selection-follow. A mid-scroll
  screenshot confirmed the app parked on Library ▸ Songs with the list moved.
  All other lists (album grids, shelves, queue) are plain static stacks.
- State plumbing: one `Rc<RefCell<AppState>>`; floem signals carry only
  revision counters — `rev` (content: nav/selection/playing/likes/queue),
  `pos` (~10 Hz playhead), `results` (search). The page is one
  `dyn_container` keyed on `(rev, view, results)`; the player bar never
  rebuilds on playhead ticks — times are reactive `label`s and seek/volume
  are signal-driven `slider`s. Bench `ScrollTo` only bumps `rev` when the
  view actually changes, so the 20 s scroll phase performs zero page
  rebuilds (scroll signal only).
- Frame pump: floem 0.2 has no timer widget, so a 30 Hz background thread
  feeds an unbounded crossbeam channel → `ext_event::create_signal_from_channel`
  → one `create_effect` runs `state.tick()` + `bench.tick()`. `--bench` is
  detected on argv; the driver is constructed on the second tick (first
  frame already painted), then the exact SPEC §7 loop; `Finish` prints the
  report to stdout and exits.
- Artwork: `state.artwork.get(seed, size)` (RGBA) → PNG-encoded
  (`image` 0.25, `png` feature) → `(seed,size)` HashMap cache, because
  floem's `img()` view decodes PNG bytes (`image::load_from_memory`).
  One-time encode per cover; rebuilds and virtual-list recycling hit cache.
- what was animated vs static: hover states are instant (no 120 ms fades —
  no transition API used), card play-scrim + red pill appear on hover
  (PointerEnter/Leave → signal → overlay with absolute positioning +
  rgba8 scrim), playing indicator is **static** 3-bar glyph, no page
  transitions.
- keyboard interactions shipped: Space, ←/→ ∓10 s, ↑/↓ selection,
  Enter play-selected, PgUp/PgDn scroll, Ctrl-K + `/` focus search,
  Esc (clear query, else back), M mute, Q queue, S shuffle, R repeat.
  Typing in the search field inhibits the single-char/space shortcuts via
  FocusGained/FocusLost tracking.
- visual divergences from the spec (honesty here is the point):
  - Native window decorations instead of custom chrome (allowed "should").
  - Card titles are single-line truncated (spec: 2-line clamp).
  - No sidebar collapse < 1000 px; grids fixed columns (5–6); queue panel
    squeezes instead of overlaying at narrow widths.
  - Playing bars static, hover changes instant (no timed fades).
  - Queue: click-jump + remove buttons; no drag reorder ("should").
  - Settings rendered, not wired (allowed).
  - Typography is real Inter (`font_family("Inter"`, system has it; the
    bundled `assets/Inter-Variable.ttf` is committed but floem 0.2 exposes
    no font-registration API, so it resolves from fontconfig).
- anything the framework made hard/easy that the next evaluator should know:
  - Easy: `virtual_list` + `scroll_to`/`on_scroll` signals did exactly what
    the bench needs; reactive labels/sliders eliminated all manual refresh
    code; the `Style` builder covers the whole design language; `svg()` took
    the iced branch's icon set with baked hex colors.
  - Hard: (1) no frame timer — the channel+thread pump is load-bearing;
    (2) `img()` only eats encoded bytes, so every cover pays a PNG encode
    (cached); the crates.io package ships **no examples**, so bootstrap,
    channel timers and scroll control all came from reading registry source;
    (3) overlay composition needs absolute positioning inside a `stack`;
    (4) `dyn_container`'s two closures + `Rc<RefCell>` + `move` produce
    partial-move borrow fights (clone the `Rc` before the first closure);
    (5) keyboard needs manual focus management (`request_focus` on the root
    at boot, focus tracking to gate Space/arrows while typing).

## Honest issues observed

- Idle RSS (~564 MB) is far above the scrolled steady state (~485 MB):
  opening on Home builds 54 album cards + shelves + text layouts, and the
  bench's switch to Library ▸ Songs tears all of that down. Both runs agree
  to 0.1 MB, so it is stable, not a leak — but Home is heavy.
- `VmHWM` (562.3 / 561.4 MB) prints *below* the startup RSS sample
  (563.9 MB), which is kernel-impossible; presumably a /proc sampling vs
  shared-page accounting quirk in the shared harness. Pasted verbatim, not
  adjusted.
- Scroll-phase CPU sat at ~33% in `ps` snapshots (report: 26–28% of one
  core over 48 s) — the 30 Hz pump + per-frame virtual-list diffing, far
  cheaper than a full rebuild design would be.
- First-ever Home paint encodes ~54 PNGs (one-time, ~100–200 ms); Albums
  tab (~600 cards) encodes on first open. Cached afterwards.
- Screenshot: `docs/gui-benchmarks/floem-home.png` (exact 1280×800 window,
  cropped from `grim`). Shelf rows intentionally overflow horizontally
  (scrollable shelves).
